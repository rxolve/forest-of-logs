# 공개 기술 노트(notes) 계획

작성일: 2026-10-09
상태: **보류 중** — 소속 조직의 확인을 받기 전까지 노트 작성을 시작하지 않는다.

## 배경

남는 주간 토큰을 더 의미 있는 곳에 쓰자는 논의에서 출발했다. 후보는 네 가지였다.

1. 이미 쌓인 운영·디버깅 지식을 공공재로 공개하기
2. 실제로 쓰는 오픈소스 라이브러리의 버그를 재현·테스트와 함께 고쳐 upstream에 보내기
3. 이미 만든 봇 프레임워크를 비영리 단체 한 곳에 무상으로 이식하기
4. 바이브코딩 서비스의 런칭 후 생존율을 추적·공개하는 사이트

1번을 우선으로 잡았고, 그 그릇으로 새 저장소 대신 이 블로그를 쓰기로 했다. 4번은 "데일리 목록"으로는 가치가 없고
생존율 추적 버전으로 좁혀야만 의미가 있다고 보아 보류했다. 2번은 비밀유지 문제가 전혀 없어 1번이 막히면 대안이 된다.

## 왜 새 저장소가 아니라 이 블로그인가

- 도메인, 정적 빌드, 한/영 렌더링, 다크 모드가 이미 있다. 새로 파면 독자 0에서 다시 시작한다.
- `/fol` 스킬의 콘텐츠 선별 필터(실패한 시도 · 미문서화 동작 · cutoff 이후 정보 · 다중 시스템 incident 서사)가
  이 목표와 정확히 같다.
- 다만 현재 형식은 목표와 어긋난다. 세션이 끝나야 쓰는 구조라 2026-04-30 이후 끊겼고, 파일명이 날짜라 검색에
  닿지 않으며, 하루키 문체 규칙("기술 용어를 나열하지 말 것")이 검색 키워드를 제목에서 지운다.
  그래서 일지(entries)는 그대로 두고 **별도 콘텐츠 타입**을 추가한다.

## 공개 범위 정책 (핵심)

내부 운영 기록을 그대로 레닥션해서 올리는 방식은 **채택하지 않는다.** 시크릿을 지워도 서사 자체가 식별자가
된다. 사용 스택 조합과 "어떤 사고가 났고 어떻게 수습했다"는 이야기만으로 소속 조직이 특정되고, 고객 영향이
있었던 건은 조직의 사고 이력을 개인 블로그에 올리는 셈이 된다.

`/fol` 필터 네 카테고리 중 식별 위험이 있는 것은 4번(incident 서사)뿐이다. 공개 대상은 아래로 한정한다.

| 카테고리 | 공개 여부 | 비고 |
|---|---|---|
| 특정 버전·환경의 미문서화 동작 | 공개 | 벤더·도구의 동작이지 조직의 이야기가 아님 |
| 모델 cutoff 이후의 정보 | 공개 | 최근 breaking change, 새 도구의 quirk |
| 실패한 시도와 그 이유 | 조건부 공개 | 벤더·도구 수준으로 추상화될 때만 |
| 다중 시스템 incident 서사 | **비공개** | 타임라인·수치·고객 영향·수습 과정은 전부 제외 |

노트 한 편의 형태는 "관찰 기록"이다. 이 버전에서 이렇게 동작한다, 재현 조건은 이것, 우회는 이것. 거기까지만 쓴다.
"우리에게 무슨 일이 있었는가"는 쓰지 않는다. 예를 들어 "결제 PG의 예약결제가 갱신 시점에 무엇을 확인하지
않는가", "ORM의 raw query가 reader/writer 중 어디로 가는가", "임베딩 API의 토큰 제한이 요청 합계인지
항목당인지" 같은 주제가 여기 해당한다.

## 선행 조건

1. **소속 조직의 확인.** "벤더·도구 동작 수준의 기술 노트를 개인 블로그에 쓰겠다"고 한 줄 확인을 받는다.
   거절이면 접고 2번(오픈소스 버그 수정)으로 간다. 조직 기술 블로그로 내자고 하면 식별 우려 자체가 사라진다.
2. 확인 전까지는 아래 구현 작업도 시작하지 않는다. 그릇만 만들어 두고 못 쓰는 상황을 피한다.

## 구현 계획 (확인 후)

1. `styles/plain.ts` 추가, `styles/index.ts` 레지스트리에 등록. 건조한 기술 산문. 1인칭 유지, 비유 없음,
   제목과 프론트매터에 기술명·버전을 그대로 둔다.
2. `content/notes/<slug>.md` 디렉토리와 로더(`app/_lib/notes.ts`), 라우트, 목록 페이지. 일지와 분리해 노출한다.
   프론트매터: `title`, `titleEn`, `date`, `style: 'plain'`, `tags`, `vendor`, `version`.
3. 이식 스킬. 입력은 세션이 아니라 이미 써둔 내부 기록 한 편. 출력은 위 정책을 통과한 공개 노트.
   세션이 없는 날에도 돌아가므로 남는 토큰을 쓰는 자리가 여기다.
4. **기계적 보안 게이트.** 지금은 보안 규칙이 글로만 있다. pre-commit에서 아래 패턴이 `content/` 안에 있으면
   커밋을 막는다: IPv4 주소, 이메일, `arn:`, EC2 인스턴스 ID(`i-0` 접두), 12자리 숫자(AWS 계정), 사용자 ID로
   보이는 숫자 ID, 홈 디렉토리 절대 경로, 조직·서비스 고유명사 목록.
5. 후보 분류. 내부 기록 전체를 위 표로 거른 후보 목록을 만들고, 순서를 정한 뒤 하루 한두 편씩 이식한다.

## 하지 않기로 한 것

- 내부 incident 기록의 레닥션 이식 (식별 위험)
- 바이브코딩 서비스 데일리 목록 사이트 (기존 서비스와 중복, 큐레이션 없으면 노이즈)
- 새 저장소·새 도메인
